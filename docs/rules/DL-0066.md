# DL-0066 · PHP ran out of memory before any script line ran (PHP2Shell probe)

**ATT&CK:** [T1190](https://attack.mitre.org/techniques/T1190/) · **Tactic:** initial-access · **Severity:** medium · **Data:** `web_server_error`

"Allowed memory size ... exhausted" with "Unknown on line 0" means PHP hit memory_limit while parsing the request, before the application started. CVE-2026-109618 is triggered exactly this way, with a large multipart POST, so a few of these from one client can be a PHP2Shell attempt. A successful exploit can still return HTTP 200, so do not wait for a crash.

## Cortex XDR (XQL)

```sql
config case_sensitive = false
| dataset = apache_httpd_raw
| filter _raw_log != null
| filter _raw_log contains "allowed memory size of" and _raw_log contains "exhausted" and _raw_log contains "unknown on line 0"
| fields _time, _raw_log
| sort desc _time
| limit 1000
```

## Splunk (SPL, Sysmon)

```
`apache_error`
| where match(_raw, "(?i)allowed\\ memory\\ size\\ of") AND match(_raw, "(?i)exhausted") AND match(_raw, "(?i)unknown\\ on\\ line\\ 0")
| table _time host _raw
| sort - _time
```

## Triage

1. Count these per client IP over a few minutes. Five or more from one source is a strong signal (see the correlation query on the rule page).
2. Check the same host for a shell under the web worker (DL-0063) and new PHP files in the web root (DL-0065).
3. Confirm the PHP version is patched and session.upload_progress.enabled is 0 until it is.

## Known false positives

- Very large legitimate form posts on servers with a small memory_limit. They come from known users and repeat the same URL.
