# DL-0041 · DSRM administrator allowed to log on normally (DsrmAdminLogonBehavior)

**ATT&CK:** [T1098](https://attack.mitre.org/techniques/T1098/), [T1112](https://attack.mitre.org/techniques/T1112/) · **Tactic:** persistence · **Severity:** critical · **Data:** `registry_set`

Setting DsrmAdminLogonBehavior to 2 lets the Directory Services Restore Mode administrator, a local account on every DC whose password rarely changes, log on over the network. An attacker who dumped that hash keeps a backdoor into the DC.

## Cortex XDR (XQL)

```sql
config case_sensitive = false
| dataset = xdr_data
| filter event_type = ENUM.REGISTRY and event_sub_type = ENUM.REGISTRY_SET_VALUE
| filter action_registry_key_name ~= "(?i)\\\\Control\\\\Lsa$" and action_registry_value_name = "dsrmadminlogonbehavior"
| fields _time, agent_hostname, actor_process_image_name, action_registry_key_name, action_registry_value_name, action_registry_data
| sort desc _time
| limit 1000
```

## Splunk (SPL, Sysmon)

```
`sysmon` EventCode=13
| eval process_name=lower(mvindex(split(Image,"\\"),-1)), reg_key=replace(TargetObject,"\\\\[^\\\\]*$",""), reg_value=mvindex(split(TargetObject,"\\"),-1)
| where match(reg_key, "(?i)\\\\Control\\\\Lsa$") AND lower(reg_value)="dsrmadminlogonbehavior"
| table _time host Image TargetObject Details
| sort - _time
```

## Triage

1. Set the value back to 0 or delete it, then reset the DSRM password on that DC (ntdsutil "set dsrm password").
2. Look for network logons by the DC's local Administrator account after the change.

## Known false positives

- Almost never set on purpose. A documented recovery procedure is the only reason.

## Tested with

1 events that must fire and 1 that must not, in [`rules/persistence/DL-0041_dsrm_network_logon_enabled.yml`](../../rules/persistence/DL-0041_dsrm_network_logon_enabled.yml).
