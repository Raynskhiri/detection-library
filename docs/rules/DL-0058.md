# DL-0058 · SID history added to an account

**ATT&CK:** [T1134.005](https://attack.mitre.org/techniques/T1134/005/) · **Tactic:** privilege-escalation · **Severity:** critical · **Data:** `windows_event`

Events 4765 and 4766 are written when SID history is added to an account, or the attempt fails. A SID from a privileged group in SID history gives those rights everywhere the SID is accepted, including across trusts without SID filtering. Outside a domain migration this should never happen.

## Cortex XDR (XQL)

```sql
config case_sensitive = false
| dataset = xdr_data
| filter event_type = ENUM.EVENT_LOG
| alter evt_subject_user = json_extract_scalar(action_evtlog_data_fields, "$.SubjectUserName"), evt_target_user = json_extract_scalar(action_evtlog_data_fields, "$.TargetUserName")
| filter action_evtlog_event_id in (4765, 4766)
| fields _time, agent_hostname, action_evtlog_event_id, evt_subject_user, evt_target_user, action_evtlog_message
| sort desc _time
| limit 1000
```

## Splunk (SPL, Sysmon)

```
`wineventlog`
| where EventCode=4765 OR EventCode=4766
| table _time host EventCode SubjectUserName TargetUserName Message
| sort - _time
```

## Triage

1. Read the SID added. -519 (Enterprise Admins) or -512 (Domain Admins) from another domain means a trust attack.
2. Clear SID history on the account and make sure SID filtering is on for external and forest trusts.

## Known false positives

- Domain migrations with ADMT. Those are planned and run from the migration account.
